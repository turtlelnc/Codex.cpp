# 用户协作开发

已确认的行为：每个成员有个人 Agent 和独立分支；项目另有共同 Agent 和共享分支。所有成员都能发消息、审批、发布自己的分支、发起明确的合并。创建者负责邀请/移除成员及配置项目模型凭据；服务不提供密钥读取接口。

第一版共同会话使用终端命令和事件流。个人 Agent 保留原有完整 TUI；这里暂未增加网页或多人聊天图形界面。

## 安装与身份

按 [服务器说明](README.md)安装，并为每位成员创建独立 SSH 账号。更新后的 `server/install.sh` 同时安装 `codex-collab.service`。升级已有服务时，先等待任务完成，再更新并重启协调服务；中断执行的恢复方式见下文。

协调器只监听 `/run/codex-collab/control.sock`，通过 Linux `SO_PEERCRED` 读取真实调用 UID。SSH 仍负责登录和加密，不接受客户端自行声明的用户名作为身份。只有 `codex-remote` 组的已登记账号能调用服务。

协调器以 root 管理身份和目录，但 Git、模型请求和工具执行均在无特权账号下运行。每个共同项目有专用的不可 SSH 登录账号；个人 Agent 使用成员自己的账号。

无项目的 `--collaborate --check` 只检查协调服务连接；项目的依赖和沙箱就绪检查使用 `--team NAME --check`。

## 创建项目、邀请与配置

```bash
./codex-cpp connect alice@server --port 2222 --collaborate
```

在协作终端输入：

```text
/create demo
/invite bob
/configure
```

也可以从不含凭据的 HTTPS 仓库创建：`/create demo https://github.com/OWNER/REPO.git`。空仓库可直接 `/create demo`，再从个人分支发布代码。初始 HTTPS 克隆暂不提供私有 Git 凭据配置；私有仓库可由成员在自己的工作区中导入后发布。

`/configure` 交互选择提供商、模型与地址，使用隐藏输入填写项目 API Key。项目配置和凭据作为一份配置原子写入 root 私有数据库，不出现在启动参数、成员事件或配置读取接口中。更新配置替换整个项目配置，后续任务使用新配置，正在运行的任务使用原配置。

项目使用 Codex 订阅时，创建者先 `/configure` 选择 `codex`，再输入 `/login`。设备登录指引只发送给创建者；成员不会收到验证码。登录凭据位于项目专用账号的私有家目录。真实订阅登录仍需在部署服务器由创建者完成，本地测试未调用真实模型服务。

成员管理仅创建者可执行：`/invite USER`、`/remove USER`。只能邀请已登记的服务器账号，不能移除创建者。移除成员会撤销新的共同会话请求、事件读取及发布权限，并取消其排队任务；如果该成员的任务正在运行，需要先等该任务结束再移除。已经克隆到成员个人目录的代码不会被删除或追回。删除 Linux 账号前，应先移除其项目成员关系并保留审计中的 UID 对应关系，避免账号 UID 复用。

## 共同 Agent

```bash
./codex-cpp connect alice@server --port 2222 --team demo
./codex-cpp connect bob@server --port 2222 --team demo
```

直接输入任务，或使用 `/send TASK`。任务按项目 FIFO 排队，共同 Agent 同一时间执行一项任务。消息、任务进度、模型结果和工具请求会成为带成员身份的事件。

```text
/status
请检查登录逻辑并补充测试
/approve APPROVAL_ID
/deny APPROVAL_ID
/quit
```

任一当前成员都能审批。审批绑定服务生成的唯一 ID；第一个有效决定生效，并记录实际审批成员。相同成员重复提交相同决定返回已记录，其他决定、旧审批 ID 均被拒绝。审批事件展示工具、调用 ID 和参数，不能通过普通聊天文字冒充审批。

客户端断线或 `/quit` 仅退出该成员的界面，后台任务继续。待审批操作不会因断线自动批准；十分钟没有决定时自动拒绝。每项 Agent 任务上限三十分钟，超时或不明中断后项目会进入待检查状态。

任务提交有 `request_id`，界面在发送前打印它。连接异常时，可使用 `/retry REQUEST_ID 原始任务文本` 查询/重试同一次消息提交；相同 ID 不重复执行，换文本会被拒绝。重新提交一个新的任务 ID 表示用户明确要求再次执行。

共享 Agent 每个排队回合启动独立进程，恢复同一份对话日志。共享会话不保留进程内 `/undo` 历史，也不支持在共同终端切换项目提供商；正式代码记录使用 `/checkpoint`，提供商由创建者 `/configure`。个人 Agent 的 `/undo`、`/provider` 等仍按原有规则工作。

## 个人开发与发布

```bash
./codex-cpp connect alice@server --port 2222 --team demo --personal
```

首次连接会从共同分支的**已提交版本**创建独立克隆，目录为 `~/workspaces/team-demo`，分支为 `users/<成员UID>`。个人未发布修改不进入共同工作区；个人模型凭据仍从该成员自己的服务器配置读取，不使用项目密钥。

个人开发完成后，先 `/quit` 退出个人 Agent，再进入共同终端：

```text
/publish 完成登录校验和测试
```

这会提交个人工作区中的修改，并把该成员的提交发布到项目仓库的个人分支，**不会合并共同分支**。发布和同步要求该成员的个人 Agent 已退出，避免程序继续写文件。其他成员的个人工作区不受影响。外部编辑器同时修改同一个个人目录仍需成员自行协调。

使用 `/sync` 将当前共同分支的已提交版本合并到自己的个人分支。有未提交修改会拒绝同步；发生冲突则撤回本次合并尝试并报告冲突文件。

项目数据通过受控 Git bundle 传输，不开放任意 Git push，也不挂载其他成员家目录。第一版单次 bundle 上限为 64 MiB。已有个人工作区会被保留；代码同步需要显式 `/sync`。已发布的个人分支只允许快进更新，改写已发布历史需要人工处理，不能用强制推送覆盖。

## 共同提交与明确合并

共同 Agent 修改后，可以审阅：

```text
/diff
/read src/example.cpp
/checkpoint 修复共同分支的配置加载
```

`/checkpoint` 展示差异和未跟踪文件，必须输入 `yes` 才提交并发布共同分支。确认绑定当前工作内容指纹；排队期间文件变化会拒绝提交，要求重新审阅。`/diff` 的大段差异可能截断，界面会标注；可用 `/read` 分别查看文件。

合并个人分支：

```text
/merge bob
```

会展示 Bob 的源提交和共同分支的目标提交。输入 `yes` 后才排队合并；执行时再次核对两个提交。没有确认、目标有未提交修改、或任一提交变化，均会停止。

Git 的正式共同分支元数据位于 Agent 工作区之外。协调器不会解释 Agent 可修改的 `.git/config`、Git hooks 或过滤器配置；完成共同提交/合并后，会刷新 Agent 的方便克隆元数据，并把旧 `.git` 移入项目私有的 `metadata-history` 目录供受限恢复。工作区文件不会因此重置。这个备份目录暂不自动清理，需要计入项目磁盘配额。

所有这些操作只更新服务器上的项目仓库，不自动推送 GitHub 或合并远端 PR。

## 分支冲突处理

1. 目标有未提交修改时，拒绝合并，先用 `/diff` 检查，再明确提交或自行处理。
2. Git 合并发生冲突时，撤回本次尝试，保留原有分支与文件，返回冲突路径；不会自动采用“我的版本”或“对方版本”。
3. 冲突成员在共同终端 `/sync`，让个人仓库取得最新共同提交。出现冲突时该尝试也会撤回，但保留 `FETCH_HEAD`。
4. 回到个人 Agent，执行 `git merge FETCH_HEAD`，让 Agent 协助解释和解决冲突；审阅文件、运行相关测试后，提交解决结果。
5. 退出个人 Agent，`/publish 解决与共同分支的冲突`，然后再次 `/merge USER`，重新确认最新提交。

例如 Alice 和 Bob 都新建了内容不同的 `conflict.txt`：Alice 先合并成功；Bob 合并时报告该文件冲突，共同分支仍保留 Alice 的内容。Bob 在个人分支生成包含双方内容的合并提交后，才能再次明确合并。自动化测试实际覆盖了此完整流程以及过期确认被拒绝的情况。

## 重启、资源与限制

重启协调服务会终止其工作进程。启动时，原先 `running` 的任务标记为 `interrupted`，项目暂停；不会自动重放未知结果的工具调用。排队任务仍保留。

管理员先检查并结束该项目专用账号残留进程，确认代码状态。创建者再 `/recover`，审阅当前差异并输入 `yes`；仍有工作进程、未处理的合并状态或审阅后文件变化时，会拒绝恢复。恢复仅继续排队任务，不重放已中断任务。不要直接把数据库中的任务改回 queued。

每个项目最多排队 100 项任务，协调器最多同时运行 16 个项目。每个创建者最多创建 10 个项目。Git/Agent 工作进程禁用 core dump、限制每 UID 的进程数和文件描述符；共享任务处于 `codex-collab.service` 的 cgroup，**不是** SSH 用户的 `user-UID.slice`。管理员应根据服务器资源配置该服务整体的 CPU/内存/TasksMax，并为项目专用 UID 设置磁盘配额和必要的进一步隔离。项目 API Key 的费用由创建者自行设置预算，第一版没有计费后台。

原执行器仍有服务器说明中记录的 Linux 安全限制。本版是受管理团队的第一版，不构成针对恶意租户的完整隔离方案；强隔离部署仍需每项目独立 VM/容器。

当前通过 84 项 C++ 自测和 31 项 Python 权限/协议测试。

```bash
./codex-self-test
python3 -m unittest discover -s tests -p 'test_*.py' -v

# 真实 C++ Agent + 本地模型夹具，完整保留 Bubblewrap
python3 tests/collaboration_agent.py ./codex-cpp

# 双 Linux UID + Unix socket + Git 冲突流程 + 真实 SSH 终端

```

容器测试环境不能挂载嵌套 procfs，因此最后一项明确使用 Agent **协议夹具**，验证真实 UID 权限、审批 IPC、分支冲突和 SSH 界面，不宣称容器内真实 Agent 可运行。真实 C++ Agent 的模型请求、排队、跨成员审批和会话恢复，在支持 Bubblewrap 的外层环境单独验证。两类证据分开报告，生产就绪检查也会拒绝不支持真实沙箱的主机。
